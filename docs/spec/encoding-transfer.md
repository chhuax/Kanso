# 编码转换与终端内文件传输规格

覆盖终端字节流的编码转换，以及在终端里进行的 ZMODEM、XMODEM 文件传输。SFTP 传输见 `ssh.md`。字节流的处理顺序见 `terminal.md` §1。

## 1. 编码转换

### 1.1 可选编码
会话对话框里提供以下选项，配置中保存 WHATWG 编码标签，统一用小写、去掉首尾空格，UTF-8 存为空：

| 显示名 | 标签 |
|---|---|
| UTF-8 | （空） |
| GB18030 — 简体中文 | gb18030 |
| GBK — 简体中文 | gbk |
| Big5 — 繁体中文 | big5 |
| Shift_JIS — 日文 | shift_jis |
| EUC-JP — 日文 | euc-jp |
| EUC-KR — 韩文 | euc-kr |
| Windows-1252 / ISO-8859-1 — 西欧 | windows-1252 |
| Windows-1251 — 西里尔 | windows-1251 |
| KOI8-R — 西里尔 | koi8-r |

### 1.2 标签解析
- 按 WHATWG 编码标准解析标签（例如 `iso-8859-1` 是 `windows-1252` 的别名）。
- 以下情况**一律按 UTF-8 处理**，保证手工编辑或导入的配置不会让终端失效：
  - 未知标签；
  - UTF-16 系列，因为它无法承载终端的控制字节；
  - "replacement" 系列（hz-gb-2312、iso-2022-cn 等），解码后没有可用内容。
  - `x-user-defined`，它把高位字节映射到私有区，显示不出可读内容；
  - `iso-2022-jp`，它靠 ESC 序列切换字符集，解码时会破坏终端自己的控制序列。
- 输出和输入两个方向**必须使用同一个解析结果**。

### 1.3 输出（远端 → 终端）
- 使用**流式**解码：多字节字符被拆在两次读取之间时，要能正确拼接。
- 解码发生在传输哨兵**之后**（见 `terminal.md` §1）。
- 每次重新连接时重置解码器，丢弃上一次会话残留的半个字符。

### 1.4 输入（键盘、粘贴 → 远端）
- 文本输入按会话编码进行编码。
- **目标编码里没有的字符编码成 `?`**。WHATWG 默认会编码成 HTML 数字实体（`&#128512;`），这些字符会原样进入 shell，所以不能用默认行为。例如 GBK 没有 emoji，GB18030 则覆盖全部 Unicode。
- **二进制写入**（传输协议、终端回应）**永远不做转换**。
- 很长的输入（例如粘贴十万个汉字）必须完整编码，不能截断。

## 2. ZMODEM

本地 shell 和 SSH 终端都会自动检测 ZMODEM。在终端里运行 `rz` 时，选择本地文件发送过去；运行 `sz <文件>` 时，为每个收到的文件选择保存位置。

### 2.1 检测
- 哨兵持续检查输出，识别 ZMODEM 握手头（ZRQINIT / ZRINIT）。普通字节原样交给终端。
- 检测到无效握手，或者已经有传输在进行时，拒绝这次握手。
- **握手头不能显示成乱码**：
  - 第一个握手头不能交给终端，否则会显示成 `**B0000…` 这样的文本。
  - 握手头被拆在两次读取之间时，前半截可能已经交给了终端：这时要清掉当前行已经显示的那部分，并丢弃这批数据剩下的字节。
- 实现：按 ZMODEM 协议文档（Chuck Forsberg 的原始规范）用 Rust 重新实现，做成不直接读写网络或文件的纯状态机 crate（`kanso-xfer`）。

### 2.2 接收（远端 `sz`）
- 进入接收状态后，提示"等待对方发送文件…"。
- 对方每提供一个文件，就提示文件名和大小（大小未知时不显示），然后**为每个文件单独弹出保存对话框**，默认文件名用对方提供的名字。
  - 用户取消：跳过这个文件，提示"已跳过"。
  - 保存失败：跳过这个文件并报错。
- 多个文件按顺序逐个处理。
- 写入本地文件时按固定大小的块流式写入，内存占用与文件大小无关。
- 结束时汇总收到了几个文件。
- **错误优先级**：本地写入失败的同时，对方恰好发完了这个文件，要报告本地磁盘错误，因为这条信息更有用。

### 2.3 发送（远端 `rz`）
- 提示"选择要发送的文件…"，弹出**可多选**的文件选择框，只能选文件，不能选目录。
- 用户取消选择：结束这次传输，提示"已取消发送"。
- 逐个发送：
  - 对方跳过某个文件时，提示"对方跳过了某某"；
  - 对方要求续传时，报错"不支持续传"；
  - 最后一个文件发完后，提示"等待对方确认"，直到对方确认完成。
- 读取本地文件时按固定大小的块读取。

### 2.4 取消与错误
- 菜单"会话 → 文件传输 → 取消传输"可以取消正在进行的 ZMODEM 或 XMODEM 传输，并向对方发送取消序列。
- 会话结束时，正在进行的传输**立即失败**。
- 报错时保留最初的原因：协议错误、网络错误还是文件系统错误，不要被后续的连带错误覆盖。
- 传输期间，键盘输入和粘贴不发往会话（见 `terminal.md` §1）。

## 3. XMODEM

XMODEM 没有可以检测的握手：接收方会直接请求第一个数据块，在此之前字节流只是普通的终端输出。所以**由用户手动启动**：先在终端里启动对方（`rx <文件>`、`sx <文件>`、bootloader 的 `loadx` 等），再从菜单选择：
- **用 XMODEM 发送…** / **用 XMODEM-1K 发送…**：选择一个文件后发送；
- **用 XMODEM 接收…**：选择保存位置后接收。

传输期间独占字节流（见 `terminal.md` §1）。

### 3.1 发送
- 对方请求 CRC（发送 `C`）时：按选定的块大小发送（128 字节或 1 KiB），使用 CRC 校验。
- 对方请求累加和（发送 NAK）时：**退回 128 字节块和累加和校验**。纯 XMODEM 早于 1K 块出现，只会累加和的接收方可能不认识 STX 头。
- 文件末尾不足一个 1K 块时，改用 128 字节块发送尾部，与 `sx -k` 的做法一致，避免大部分内容都是填充。
- 收到 NAK 或超时，就重发当前块。
- 对方打开阶段重复发送的 `C`，只在第一块之前视为 NAK；之后出现的其他字节当作噪声，CAN 除外。
- 发送 EOT 后，等对方确认才算完成。

### 3.2 接收
- **先请求 CRC**，连续三次 `C` 都没有回应时，改为发 NAK，请求累加和，兼容不支持 `C` 的老发送方。
- 校验方式**由收到的第一个数据块决定**，不管之前请求的是哪种：第一块后面跟两个校验字节就是 CRC，跟一个就是累加和。
- 同时接受 128 字节块（SOH）和 1 KiB 块（STX）。
- 对方因为没收到我们的 ACK 而重发同一块时，确认它，但不重复写入。
- 第一块到来之前出现的其他字节（命令行回显、横幅），当作普通终端输出处理。
- **XMODEM 不携带文件大小**，所以收到的文件末尾会保留发送方填充的 `^Z`。这一点在帮助文档里要说明。
- 超时：每个数据块最多等 10 秒，与原始协议一致；字节之间的超时比规范的 1 秒宽松，因为数据是成批到达的。

### 3.3 对话框打开期间
- 用户还在选择文件时，对方的开局请求可能已经到达：先暂存这些字节，用户选好文件后立即响应，不必等对方下一次重试。
- 用户在对话框里取消时，把暂存的字节交给终端显示，就像什么都没发生过一样。
- 用户选择文件期间，接收方可能已经从 CRC 模式退到了 NAK 模式，要以**最新收到的请求**为准。

### 3.4 结束与取消
- 传输结束后才到达的字节（比如远端的提示符）属于终端，要交给终端显示。传输失败时剩下的字节同样交给终端。
- 对方已经发送了取消序列时，不要再回发取消；已经结束的传输也不再发送。
- 失败时先通知对方，再报告错误。

## 4. 实现约束

- `kanso-encoding` 和 `kanso-xfer` 都是纯逻辑 crate，不直接读写网络或文件；字节输入、输出、计时和文件访问都由调用方注入。这样既方便测试，将来也可以单独以 MIT 协议开源。
- 测试分两层：XMODEM 用内存中的两端对传进行测试；ZMODEM 和 XMODEM 都要与 `lrzsz` 的实际程序互传测试。

## 5. 验收用例

- GBK 会话里输入"ls 你好"，远端收到正确的 GBK 字节；输入 emoji 时，远端收到 `?`。
- GB18030 会话能完整收发 emoji。
- 多字节字符被拆在两次读取之间时，显示正确。
- 未知标签、`utf-16`、`hz-gb-2312` 都按 UTF-8 处理。
- 远端运行 `sz` 发送三个文件，取消第二个文件的保存对话框：第一个和第三个保存成功，第二个提示已跳过。
- 终端里不出现 `**B0000` 这样的握手乱码。
- 与只支持累加和的发送方、只支持累加和的接收方都能完成 XMODEM 传输。
- 发送方重复发送同一块时，接收的文件不会重复写入这一块。
- 在保存对话框里取消 XMODEM 接收后，终端恢复正常，之前暂存的输出也显示出来。
- 传输过程中关闭会话，传输立即报错结束。
